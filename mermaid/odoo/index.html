Odoo 18 Development
Manual.

A single-page reference for building custom Odoo 18 addons — from installing the server on Windows, Linux and GitHub Codespaces, to the file structure, XML views, menus, security rules, QWeb reports, controllers and the external API. Written for someone opening an Odoo module for the first time.

01 / GETTING STARTED

Install Odoo 18 on Windows

Two options exist: the one-click Windows installer (fastest, good for trying Odoo) or a source install (recommended for development, since you can edit code and add custom addons directly).

Option A — Windows installer (quick start)

1

Download the installer

Get the .exe for Odoo 18 from odoo.com/page/download. It bundles Python, PostgreSQL and all dependencies — nothing else to install.

2

Run the setup wizard

Accept defaults for the install path, PostgreSQL port and Odoo port (8069). The installer registers Odoo as a Windows service, so it starts automatically on boot.

3

Open Odoo

Visit http://localhost:8069 in your browser and create your first database.

LimitationThe installer build is meant for evaluation. For real addon development, use the source install below — it gives you a visible, editable addons/ folder and lets you restart the server from a terminal with debug flags.

Option B — Source install (recommended for developers)

1

Install Python 3.10+

Download from python.org. During setup, tick "Add Python to PATH".

2

Install PostgreSQL

Install PostgreSQL 15/16 from postgresql.org. Create a database superuser, e.g. odoo, with a password you'll remember — this becomes db_user / db_password in odoo.conf.

3

Install Git and clone the source

powershell 
git clone https://github.com/odoo/odoo.git --branch 18.0 --depth 1 C:\odoo18
4

Install wkhtmltopdf

Needed for PDF report rendering (QWeb → PDF). Install the Odoo-patched build (version 0.12.6) — the stock wkhtmltopdf breaks headers/footers in reports.

5

Create a virtual environment & install requirements

powershell 
cd C:\odoo18
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
6

Run the server

powershell 
python odoo-bin -r odoo -w yourpassword --addons-path=addons -d mydb

Open http://localhost:8069.

02 / GETTING STARTED

Install Odoo 18 on Linux (Ubuntu/Debian)

Source install, so you get a proper development setup with an editable addons path and a dedicated system user.

1

Update & install system dependencies

bash 
sudo apt update && sudo apt upgrade -y
sudo apt install -y git python3-pip build-essential wget python3-dev \
  python3-venv python3-wheel libxslt-dev libzip-dev libldap2-dev \
  libsasl2-dev python3-setuptools node-less libjpeg-dev zlib1g-dev \
  libpq-dev libxml2-dev libffi-dev
2

Install & configure PostgreSQL

bash 
sudo apt install -y postgresql
sudo -u postgres createuser -s $USER
# or create a dedicated role for odoo:
sudo -u postgres createuser --createdb --pwprompt odoo18
3

Create a system user for Odoo (optional but recommended)

bash 
sudo adduser --system --home=/opt/odoo18 --group odoo18
4

Clone Odoo source

bash 
sudo git clone https://github.com/odoo/odoo.git --branch 18.0 --depth 1 /opt/odoo18/odoo
5

Virtual environment & Python dependencies

bash 
cd /opt/odoo18/odoo
python3 -m venv odoo-venv
source odoo-venv/bin/activate
pip3 install wheel
pip3 install -r requirements.txt
6

Install wkhtmltopdf (for reports)

bash 
sudo apt install -y wkhtmltopdf   # or the Odoo-patched .deb for 0.12.6
7

Create your custom addons folder

bash 
mkdir -p /opt/odoo18/custom-addons

This is where your modules live, kept separate from Odoo's own addons/ — see section 05.

8

Run from source (development mode)

bash 
./odoo-bin --addons-path=addons,/opt/odoo18/custom-addons \
  -r odoo18 -w yourpassword -d mydb

Visit http://localhost:8069. For a permanent setup, write an odoo.conf and a systemd service — see 07 and 08.

03 / GETTING STARTED

Run Odoo 18 in GitHub Codespaces

Codespaces gives you a full Linux dev container in the browser — no local setup, good for freshers who just want to write module code fast.

1

Fork/create a repository

Create a GitHub repo for your custom addons (e.g. my-odoo-addons), or fork odoo/odoo if you also want the core source editable.

2

Open a Codespace

On the repo page: Code → Codespaces → Create codespace on main. Choose a machine type with at least 4 cores / 8 GB RAM — Odoo plus PostgreSQL is heavier than a typical web app.

3

Add a devcontainer (recommended)

Create .devcontainer/devcontainer.json so the environment rebuilds identically every time:

.devcontainer/devcontainer.json 
{
  "name": "odoo18-dev",
  "image": "mcr.microsoft.com/devcontainers/base:ubuntu",
  "features": {
    "ghcr.io/devcontainers/features/python:1": { "version": "3.11" },
    "ghcr.io/devcontainers-contrib/features/postgres-asdf:1": {}
  },
  "forwardPorts": [8069, 5432],
  "postCreateCommand": "bash .devcontainer/setup.sh"
}
.devcontainer/setup.sh 
#!/bin/bash
sudo apt-get update
sudo apt-get install -y git python3-dev libxslt-dev libzip-dev \
  libldap2-dev libsasl2-dev libpq-dev wkhtmltopdf
sudo service postgresql start
sudo -u postgres createuser -s $(whoami) || true
git clone https://github.com/odoo/odoo.git --branch 18.0 --depth 1 odoo
python3 -m venv venv
source venv/bin/activate
pip install -r odoo/requirements.txt
4

Start the server

bash 
source venv/bin/activate
./odoo/odoo-bin --addons-path=odoo/addons,custom-addons -d mydb
5

Open the forwarded port

Codespaces auto-detects port 8069 and offers "Open in Browser" — set its visibility to Public temporarily if you need to share a demo link.

Why Codespaces is handy for freshersYou get a disposable, identical Linux environment every time — no "works on my machine" issues, and you can throw the codespace away and rebuild it in minutes if you break your Python environment.
04 / PROJECT LAYOUT

Odoo file structure (server root)

This is what the cloned odoo/ source tree looks like — you rarely edit these folders directly; instead you point addons-path at your own custom addons directory.

odoo18/ ├── odoo-bin # entry point script — starts the server ├── odoo/ # core framework (ORM, http, tools, fields...) │ ├── addons/ # base modules shipped with the framework │ ├── cli/ │ ├── fields.py │ ├── models.py │ ├── http.py │ └── modules/ ├── addons/ # official Community apps (sale, stock, hr...) ├── enterprise/ # Enterprise apps — separate repo, needs a license ├── requirements.txt ├── setup.py └── debian/, doc/, ...
pathpurpose
odoo-binThe executable you run: ./odoo-bin -c odoo.conf. Boots the server, loads config, loads modules.
odoo/The framework itself: ORM, ir.* system models, HTTP routing, QWeb engine, tools. Do not edit.
addons/Official Community modules — base, web, sale, stock, account, etc.
enterprise/Enterprise-only apps (Studio, Accounting extras, Helpdesk, Sign...) — a separate git repo cloned alongside; requires a valid Enterprise subscription/license key to activate.
Community vs EnterpriseBoth editions share the exact same core (odoo/) and the exact same module structure/APIs described in this manual. Enterprise simply adds an extra addons-path (the enterprise/ folder) with more modules and a different web theme. Anything you learn here about models, views, security and reports applies identically to both.
05 / PROJECT LAYOUT

Where your custom addons folder goes

Never place your own modules inside Odoo's addons/ folder — it makes upgrades painful and mixes your code with core code. Instead, keep a sibling folder and register it via addons_path.

/opt/odoo18/ # a common layout on a Linux server ├── odoo/ # core source (cloned from github) │ └── addons/ ├── enterprise/ # optional, Enterprise modules ├── custom-addons/ # ← YOUR modules live here │ ├── my_first_module/ │ └── my_second_module/ ├── odoo-venv/ # python virtual environment. ├── odoo.conf └── odoo-data/ # filestore, sessions (filestore path)
odoo.conf — register the custom path 
[options]
addons_path = /opt/odoo18/odoo/addons,/opt/odoo18/enterprise,/opt/odoo18/custom-addons
Rule of thumbList paths from most "core" to most "custom": Odoo addons → Enterprise → your custom-addons. If two folders define a module with the same technical name, the one found first on the path wins — so keep your custom modules uniquely named (e.g. prefix with your company code: acme_sale_extension).
06 / PROJECT LAYOUT

Anatomy of a single module

Every Odoo addon is just a Python package (a folder with an __init__.py) plus a __manifest__.py descriptor. This is the conventional layout used across almost every real-world module.

custom-addons/ └── my_first_module/ ├── __init__.py # imports the models/ package ├── __manifest__.py # module descriptor (see §09) ├── models/ │ ├── __init__.py # imports each model file │ └── my_model.py ├── views/ │ ├── my_model_views.xml # form/list/search views. │ └── my_model_menus.xml # menu items + window actions ├── security/ │ ├── ir.model.access.csv # model-level access rights │ └── my_model_security.xml # groups + record rules ├── controllers/ │ ├── __init__.py │ └── main.py # custom HTTP routes ├── report/ │ ├── my_report.xml # QWeb report template │ └── my_report_action.xml ├── wizard/ # transient models for popups │ ├── __init__.py │ └── my_wizard.py ├── data/ # demo/seed XML or CSV data │ └── my_model_data.xml ├── static/ │ ├── description/ │ │ ├── icon.png # module icon in Apps list │ │ └── index.html │ └── src/ │ ├── js/ │ ├── scss/ │ └── xml/ # OWL component templates └── i18n/ # .pot / .po translation files
folder / filewhat it holds
__init__.py (root)Usually just from . import models, controllers, wizard.
models/Python classes inheriting models.Model, models.TransientModel or extending existing ones.
views/XML defining how records are displayed: form, list, kanban, search, calendar...
security/ir.model.access.csv (CRUD per group) and optional record rules / group definitions.
controllers/Python classes exposing custom URLs via @http.route.
report/QWeb templates rendered to PDF/HTML, plus the ir.actions.report record.
wizard/Transient models backing pop-up dialogs (e.g. "Confirm" wizards).
data/Non-demo XML/CSV loaded on install — sequences, mail templates, default records.
static/description/icon.png128×128 PNG shown for the module in Apps.
Naming conventionModel x_project.task.extra → Python file models/project_task_extra.py → view file views/project_task_extra_views.xml. Consistent naming is what keeps a module readable six months later.
07 / PROJECT LAYOUT

odoo.conf — the server configuration file

A plain INI file read at startup with -c /path/to/odoo.conf. It replaces long command-line flags for a permanent install.

/etc/odoo18.conf 
[options]
; ----- database -----
db_host = localhost
db_port = 5432
db_user = odoo18
db_password = your_db_password
;dbfilter = ^mydb$          ; restrict which DB(s) this instance can see

; ----- addons -----
addons_path = /opt/odoo18/odoo/addons,/opt/odoo18/enterprise,/opt/odoo18/custom-addons

; ----- network -----
xmlrpc_port = 8069          ; main HTTP port (called http_port in 17+)
;gevent_port = 8072         ; longpolling / websocket port

; ----- filesystem -----
data_dir = /opt/odoo18/odoo-data     ; filestore, sessions

; ----- process / performance -----
workers = 4                 ; 0 = dev mode (single-threaded, auto-reload friendly)
max_cron_threads = 2
limit_time_cpu = 600
limit_time_real = 1200

; ----- security -----
admin_passwd = a_strong_master_password   ; protects db manage screens

; ----- logging -----
logfile = /var/log/odoo18/odoo.log
log_level = info            ; debug, info, warn, error
keymeaning
addons_pathComma-separated folders scanned for modules — this is where you add your custom-addons directory.
admin_passwdThe "master password" used on the database manager screen (create/drop/duplicate/backup DB) — not a user login.
workers0 for development (auto-reload, easier debugging); a positive number (e.g. 2×CPU cores + 1) for production multi-processing.
dbfilterRegex limiting which databases this Odoo instance will serve — important once you have several customers/databases on one server.
data_dirWhere the filestore (uploaded attachments/images) and sessions are stored on disk.
logfile / log_levelWhere logs are written and how verbose they are — see next section.
Fresher tipDuring development, run with workers = 0 and add --dev=all on the command line — this enables auto-reload on file save and better tracebacks in the browser.
08 / PROJECT LAYOUT

Running Odoo as a service, and reading logs

systemd service (Linux)

Instead of running ./odoo-bin in a terminal you leave open, register Odoo as a background service that survives reboots.

/etc/systemd/system/odoo18.service 
[Unit]
Description=Odoo18
Requires=postgresql.service
After=network.target postgresql.service

[Service]
Type=simple
SyslogIdentifier=odoo18
PermissionsStartOnly=true
User=odoo18
Group=odoo18
ExecStart=/opt/odoo18/odoo-venv/bin/python3 \
  /opt/odoo18/odoo/odoo-bin -c /etc/odoo18.conf
StandardOutput=journal+console
Restart=always

[Install]
WantedBy=multi-user.target
bash — enable & control the service 
sudo systemctl daemon-reload
sudo systemctl enable --now odoo18       # start on boot + start now
sudo systemctl restart odoo18            # after a code/config change
sudo systemctl status odoo18             # is it running?
sudo journalctl -u odoo18 -f             # live service logs (via journald)

Log files

If logfile is set in odoo.conf, Odoo writes there instead of stdout. Tail it while developing:

bash 
tail -f /var/log/odoo18/odoo.log
grep -i error /var/log/odoo18/odoo.log
grep -i "my_module" /var/log/odoo18/odoo.log
log leveluse
debugEverything, including SQL-adjacent internals — very verbose, dev only.
infoDefault — module loading, HTTP requests, cron runs.
warnOnly warnings and errors — good for a quiet production log.
errorOnly failures — tracebacks, unhandled exceptions.
Where to look first when something breaks90% of module install/upgrade errors show a Python traceback at the end of the log right after a line like odoo.modules.registry: Failed to load registry. Scroll to the bottom of the traceback, not the top — the last line is usually the real cause.
09 / MODULE ANATOMY

__manifest__.py

A plain Python dictionary describing the module: its name, dependencies, and every data file to load, in order.

my_first_module/__manifest__.py 
{
    'name': 'My First Module',
    'version': '18.0.1.0.0',
    'category': 'Sales',
    'summary': 'Short one-line summary shown in the Apps list',
    'description': """
        Longer description, can use RST/markdown-ish text.
    """,
    'author': 'Your Company',
    'website': 'https://example.com',
    'license': 'LGPL-3',

    # other modules this one needs installed first
    'depends': ['base', 'sale'],

    # every XML/CSV file to load, IN ORDER (security before views that use it,
    # views before menus that reference them)
    'data': [
        'security/my_model_security.xml',
        'security/ir.model.access.csv',
        'views/my_model_views.xml',
        'views/my_model_menus.xml',
        'report/my_report.xml',
        'data/my_model_data.xml',
    ],

    # only loaded when running with --test-enable or demo data
    'demo': [
        'demo/my_model_demo.xml',
    ],

    # front-end assets (JS/SCSS/OWL templates)
    'assets': {
        'web.assets_backend': [
            'my_first_module/static/src/js/my_widget.js',
            'my_first_module/static/src/scss/my_style.scss',
        ],
    },

    'installable': True,
    'application': True,   # shows as a top-level "App", not just a module
    'auto_install': False,
}
keymeaning
versionConvention: {odoo_version}.{module_version}, e.g. 18.0.1.0.0.
dependsList of module technical names that must be installed first — their models/views become available to yours.
dataFiles always loaded on install/upgrade. Order matters: security and base records before the views/menus that depend on them.
demoSample data loaded only when demo data is enabled (useful for testing, not for production).
assetsOdoo 18 way of bundling JS/SCSS/XML front-end assets into named bundles like web.assets_backend.
applicationTrue makes it appear as its own icon on the Apps home screen rather than being a hidden technical module.
10 / MODULE ANATOMY

Python models & the ORM

Models are Python classes mapped automatically to PostgreSQL tables by Odoo's ORM. You almost never write raw SQL.

Creating a new model

models/my_model.py 
from odoo import api, fields, models


class MyModel(models.Model):
    _name = 'my.model'
    _description = 'My Model'
    _order = 'sequence, name'

    name = fields.Char(string='Name', required=True)
    sequence = fields.Integer(default=10)
    active = fields.Boolean(default=True)
    date_deadline = fields.Date()
    amount = fields.Monetary(currency_field='currency_id')
    currency_id = fields.Many2one('res.currency')
    partner_id = fields.Many2one('res.partner', string='Customer')
    line_ids = fields.One2many('my.model.line', 'model_id', string='Lines')
    tag_ids = fields.Many2many('my.model.tag', string='Tags')
    state = fields.Selection([
        ('draft', 'Draft'),
        ('confirmed', 'Confirmed'),
        ('done', 'Done'),
    ], default='draft', tracking=True)

    total = fields.Float(compute='_compute_total', store=True)

    @api.depends('line_ids.subtotal')
    def _compute_total(self):
        for rec in self:
            rec.total = sum(rec.line_ids.mapped('subtotal'))

    def action_confirm(self):
        self.write({'state': 'confirmed'})

    @api.model
    def create(self, vals):
        # customise creation logic, then call super()
        return super().create(vals)

Extending an existing model

Use _inherit without _name to add fields/methods to a model that already exists (e.g. adding a field to res.partner):

models/res_partner.py 
from odoo import fields, models


class ResPartner(models.Model):
    _inherit = 'res.partner'

    loyalty_points = fields.Integer(string='Loyalty Points', default=0)

11 / MODULE ANATOMY

XML views

Views declare how a model's records are displayed. All view records are stored in ir.ui.view. In Odoo 18 the list view type is written as <list> (the old <tree> tag still works but list is now the canonical name).

Form view

views/my_model_views.xml 
<odoo>
  <record id="view_my_model_form" model="ir.ui.view">
    <field name="name">my.model.form</field>
    <field name="model">my.model</field>
    <field name="arch" type="xml">
      <form string="My Model">
        <header>
          <button name="action_confirm" type="object"
                  string="Confirm" class="btn-primary"
                  invisible="state != 'draft'"/>
          <field name="state" widget="statusbar"/>
        </header>
        <sheet>
          <group>
            <field name="name"/>
            <field name="partner_id"/>
            <field name="date_deadline"/>
          </group>
          <notebook>
            <page string="Lines">
              <field name="line_ids">
                <list editable="bottom">
                  <field name="product_id"/>
                  <field name="subtotal"/>
                </list>
              </field>
            </page>
          </notebook>
        </sheet>
      </form>
    </field>
  </record>
</odoo>

List view (formerly "tree")

<record id="view_my_model_list" model="ir.ui.view">
  <field name="name">my.model.list</field>
  <field name="model">my.model</field>
  <field name="arch" type="xml">
    <list decoration-danger="state == 'draft'">
      <field name="name"/>
      <field name="partner_id"/>
      <field name="total" sum="Total"/>
      <field name="state"/>
    </list>
  </field>
</record>

Search view

<record id="view_my_model_search" model="ir.ui.view">
  <field name="name">my.model.search</field>
  <field name="model">my.model</field>
  <field name="arch" type="xml">
    <search>
      <field name="name"/>
      <field name="partner_id"/>
      <filter string="Draft" name="filter_draft" domain="[('state','=','draft')]"/>
      <group expand="0" string="Group By">
        <filter string="Customer" name="group_partner" context="{'group_by':'partner_id'}"/>
      </group>
    </search>
  </field>
</record>

Kanban view (short example)

<record id="view_my_model_kanban" model="ir.ui.view">
  <field name="name">my.model.kanban</field>
  <field name="model">my.model</field>
  <field name="arch" type="xml">
    <kanban>
      <templates>
        <t t-name="card">
          <div class="oe_kanban_card">
            <strong><field name="name"/></strong>
            <div><field name="partner_id"/></div>
          </div>
        </t>
      </templates>
    </kanban>
  </field>
</record>
invisible / readonly / requiredSince Odoo 17+, view attribute modifiers are written as plain Python-like expressions directly on the element, e.g. invisible="state != 'draft'", rather than the older attrs="{'invisible': [...]}" dictionary syntax. Odoo 18 keeps this simplified syntax.
12 / MODULE ANATOMY

Menus & window actions

A menu item is just a clickable label; it does nothing by itself. It points to an action (usually ir.actions.act_window) which tells Odoo which model and which views to open.

views/my_model_menus.xml 
<odoo>
  <!-- 1. the action: what to open -->
  <record id="action_my_model" model="ir.actions.act_window">
    <field name="name">My Models</field>
    <field name="res_model">my.model</field>
    <field name="view_mode">list,form,kanban</field>
    <field name="context">{'search_default_filter_draft': 1}</field>
    <field name="help" type="html">
      <p class="o_view_nocontent_smiling_face">Create your first record</p>
    </field>
  </record>

  <!-- 2. top-level (root) menu -->
  <menuitem id="menu_my_module_root"
            name="My Module"
            sequence="10"
            web_icon="my_first_module,static/description/icon.png"/>

  <!-- 3. a category under the root -->
  <menuitem id="menu_my_model_category"
            name="Configuration"
            parent="menu_my_module_root"
            sequence="90"/>

  <!-- 4. the clickable leaf menu, linked to the action -->
  <menuitem id="menu_my_model"
            name="My Models"
            parent="menu_my_module_root"
            action="action_my_model"
            sequence="10"/>
</odoo>
elementrole
ir.actions.act_windowOpens a model with given views (list/form/kanban/...); optional default domain/context/filters.
<menuitem> (root, no action)A top-level app entry / folder — needs web_icon to appear on the Apps switcher.
<menuitem> (with action)A clickable leaf that actually opens something.
sequenceControls left-to-right / top-to-bottom ordering among siblings.
Load order mattersThe action must be defined before the menuitem that references it in the same file (top-to-bottom), and this XML file itself must appear after the security files in __manifest__.py's data list.
13 / MODULE ANATOMY

Security: groups, access rights, record rules

Odoo security has three layers. Get comfortable with all three — a missing access line is the #1 error freshers hit ("You are not allowed to access...").

1. Access rights — ir.model.access.csv

One line per (model, group) pair defining CRUD permissions. Required for every model you create — without it, nobody (not even the admin) can use it.

security/ir.model.access.csv 
id,name,model_id:id,group_id:id,perm_read,perm_write,perm_create,perm_unlink
access_my_model_user,my.model.user,model_my_model,base.group_user,1,1,1,0
access_my_model_manager,my.model.manager,model_my_model,my_first_module.group_my_model_manager,1,1,1,1
columnmeaning
model_id:idXML ID of the model, auto-generated as model_<model_name_with_underscores>, e.g. my.model → model_my_model.
group_id:idThe security group this row applies to; leave empty to apply to everyone (rare, avoid for real apps).
perm_read/write/create/unlink1/0 flags — read, edit, create, delete respectively.

2. Security groups

security/my_model_security.xml 
<odoo>
  <record id="module_category_my_module" model="ir.module.category">
    <field name="name">My Module</field>
  </record>

  <record id="group_my_model_user" model="res.groups">
    <field name="name">User</field>
    <field name="category_id" ref="module_category_my_module"/>
  </record>

  <record id="group_my_model_manager" model="res.groups">
    <field name="name">Manager</field>
    <field name="category_id" ref="module_category_my_module"/>
    <field name="implied_ids" eval="[(4, ref('group_my_model_user'))]"/>
  </record>
</odoo>

3. Record rules (row-level security)

Restrict which rows a group can see/edit, using a domain — e.g. "users can only see their own records":

<record id="rule_my_model_own_only" model="ir.rule">
  <field name="name">My Model: own records only</field>
  <field name="model_id" ref="model_my_model"/>
  <field name="domain_force">[('create_uid', '=', user.id)]</field>
  <field name="groups" eval="[(4, ref('group_my_model_user'))]"/>
</record>
Order of evaluationAccess rights (CSV) decide if a user can touch the model at all (coarse, per-model). Record rules then filter which rows (fine, per-record). Both must allow an action for it to succeed.

QWeb reports (PDF/HTML)

QWeb is Odoo's XML templating engine. Reports combine a QWeb template with an ir.actions.report record that hooks it to a "Print" button, and are rendered to PDF via wkhtmltopdf.

report/my_report.xml — the template 
<odoo>
  <template id="report_my_model_document">
    <t t-call="web.html_container">
      <t t-foreach="docs" t-as="o">
        <t t-call="web.external_layout">
          <div class="page">
            <h2>Document: <span t-field="o.name"/></h2>
            <p>Customer: <span t-field="o.partner_id.name"/></p>
            <table class="table table-sm">
              <thead>
                <tr><th>Product</th><th>Subtotal</th></tr>
              </thead>
              <tbody>
                <tr t-foreach="o.line_ids" t-as="line">
                  <td><span t-field="line.product_id.name"/></td>
                  <td><span t-field="line.subtotal"/></td>
                </tr>
              </tbody>
            </table>
            <p>Total: <span t-field="o.total"/></p>
          </div>
        </t>
      </t>
    </t>
  </template>
</odoo>
report/my_report_action.xml — the print action 
<odoo>
  <record id="action_report_my_model" model="ir.actions.report">
    <field name="name">My Model Document</field>
    <field name="model">my.model</field>
    <field name="report_type">qweb-pdf</field>
    <field name="report_name">my_first_module.report_my_model_document</field>
    <field name="report_file">my_first_module.report_my_model_document</field>
    <field name="print_report_name">'Document - %s' % object.name</field>
    <field name="binding_model_id" ref="model_my_model"/>
    <field name="binding_type">report</field>
  </record>
</odoo>
QWeb directiveuse
t-foreach / t-asLoop over a recordset.
t-fieldPrint a field with its correct widget/formatting (dates, currency...).
t-if / t-elseConditional rendering.
t-escPrint a raw Python expression, HTML-escaped.
web.external_layoutStandard header/footer (company logo, address) reused across reports.
binding_model_id + binding_typeSetting these makes the report automatically appear under the record's Print menu — no extra button XML needed.

Controllers (custom web routes)

Controllers expose plain HTTP endpoints outside the standard backend UI — useful for public pages, webhooks, custom JSON endpoints, or portal pages.

controllers/main.py 
from odoo import http
from odoo.http import request


class MyModelController(http.Controller):

    @http.route('/my_module/hello', type='http', auth='public', website=True)
    def hello(self, **kwargs):
        return request.render('my_first_module.hello_page_template', {
            'message': 'Hello from a controller!',
        })

    @http.route('/my_module/api/records', type='json', auth='user')
    def list_records(self, **kwargs):
        records = request.env['my.model'].search_read(
            [], ['id', 'name', 'total']
        )
        return {'records': records}

    @http.route('/my_module/webhook', type='http', auth='public',
                methods=['POST'], csrf=False)
    def webhook(self, **post):
        request.env['my.model'].sudo().create({'name': post.get('name')})
        return 'ok'
route argumentmeaning
type='http'Returns a full HTTP response (HTML page, redirect, file).
type='json'Returns JSON, matches Odoo's internal RPC calling convention.
auth='public'No login required.
auth='user'Requires an authenticated Odoo session.
website=TrueWraps the response in the Website module's header/footer.
csrf=FalseDisables CSRF token check — needed for external webhooks that can't send Odoo's token.
sudo() with careUse .sudo() to bypass access rights only when the endpoint's own auth level already establishes who is allowed to call it — never as a shortcut to skip writing proper security rules.

External API (XML-RPC / JSON-RPC)

Any external application (a script, another server, a mobile app) can talk to Odoo the same way the web client does — over XML-RPC or JSON-RPC — without installing anything on the Odoo side.

python — external client example 
import xmlrpc.client

url = 'http://localhost:8069'
db = 'mydb'
username = 'admin'
password = 'admin'

common = xmlrpc.client.ServerProxy(f'{url}/xmlrpc/2/common')
uid = common.authenticate(db, username, password, {})

models = xmlrpc.client.ServerProxy(f'{url}/xmlrpc/2/object')

# search + read in one call
records = models.execute_kw(
    db, uid, password,
    'my.model', 'search_read',
    [[['state', '=', 'draft']]],
    {'fields': ['name', 'partner_id', 'total'], 'limit': 20}
)

# create a record
new_id = models.execute_kw(
    db, uid, password,
    'my.model', 'create',
    [{'name': 'Created via API'}]
)

# call a custom method
models.execute_kw(db, uid, password, 'my.model', 'action_confirm', [[new_id]])
endpointuse
/xmlrpc/2/commonAuthentication (authenticate, version).
/xmlrpc/2/objectCalls any model method via execute_kw(db, uid, password, model, method, args, kwargs).
/jsonrpcSame capabilities as XML-RPC, using JSON-RPC 2.0 — handy from JS/Node clients.
Same rules applyEvery external API call still passes through the exact same access rights and record rules described in §13 — the API user's group memberships fully determine what it can read or write.
